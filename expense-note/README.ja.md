# Expense note

一社ぶんの社内経費メモです。社員は発行されたアカウントでサインインし、支払った内容 — 日付・金額・カテゴリ・メモ — を記録し、自分の記録を訂正・削除し、月を1つ選んでその合計とともに読みます。

他人の記録は誰にも見えず、承認もなく、管理者もいません。これで全部で、意図的にこの大きさに絞ってあります。

## 仕様書

[`specs/1.0.0/spec.md`](./specs/1.0.0/spec.md) — 349行、3つの機能、7つの operation、3つの画面。

**`/hora-spec` が書いたままの文書です。** 後から整形はしていません。

## 書くのに何があったか

**ステージ0は何も読んでいません。** 読むものが無かったからです — 新規プロジェクト、リポジトリなし、文書なし、要望は `request/` ではなく会話で述べられたもの。

**ステージ1に入る前に4つ質問しました** — このセッションから届かない場所に文書があるか、利用者は何種類か、アカウントはどう発行されるか、`/hora` が質問を書く言語はどれか。うち3つの答えが文書の形を決めました。

- **アクターは1つ。** 自分の経費を自分で管理する社員
- **アカウントは運用者が発行する**（プロダクトの外で）。よってサインアップ画面はなく、管理者アクターもおらず、`Actors and roles` の表は1行
- **質問は英語**

それ以外はすべて提案として提示し、承認されたもののみ書かれています — 3つの機能、すべてのユースケース、すべての受け入れ基準、データモデル、operation、画面。

## この実行が決めたこと、そしてその在り処

| | 場所 |
|---|---|
| **自分の記録を読むのは `#expense-entry` であって `#monthly-summary` ではない** — 逆にすると `#expense-entry` のユースケースが後から作る機能を指してしまい、`/hora-plan` が止める | 11章・12章 |
| **先送りは3つ、それぞれ必要な seam を明記** — 承認のために最初のマイグレーションから持つ `status` カラム、エクスポートのために月の一覧と合計を1つの operation が返すこと、カテゴリを enum ではなく行にすること | 4章 |
| **バックグラウンドジョブが無いので Redis も宣言しない** — すべての書き込みはリクエスト内で完結する | 8章 |
| **エンドポイントは1つ、認証主体も1つ**、理由も明記 — 1.1.0 のマネージャーは同じログインの role であって、2つ目のサーバーではない | 2章・7章 |
| **他人の経費は forbidden ではなく not found として返す** | 11章・12章 |
